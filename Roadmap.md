# DeepStegAI-V2 Pragmatic Architecture Roadmap 🗺️🛡️

This document provides a neutral, risk-based assessment and a phased execution plan for transitioning **DeepStegAI-V2** from a high-performance development state to a production-grade forensic suite.

---

## 1. CURRENT STATE ASSESSMENT
*   **Production Readiness**: **Not yet.** While feature-complete, the system currently lacks production-grade process management (Running on Flask/Vite dev servers) and resilient worker handling for AI processing.
*   **Strong Parts**: Core forensic pipeline, authenticated credit economy, cinematic UI/UX, and robust SMTP integration.
*   **Fragile Parts**: 
    *   **Synchronous Processing**: AI inference (PyTorch) blocks Flask threads, leading to potential timeouts during high concurrency.
    *   **Local Persistence**: Reliance on the local filesystem for uploads is a bottleneck for multi-instance scaling.

---

## 2. DECISION ANALYSIS

| Topic | Recommendation | Reasoning |
| :--- | :--- | :--- |
| **Docker** | **Later** | Implementing Docker now adds networking overhead without a clear benefit for a single-server deployment. Prioritize stability in the native environment first. |
| **Async Processing** | **Yes (High)** | Necessary to offload heavy PyTorch inference from the main API thread to prevent server hanging during long scans. |
| **Cloud Storage** | **Later** | Keep local storage for Phase 1 to minimize costs. Move to S3/equivalent only when horizontal scaling becomes a hard requirement. |
| **Architecture** | **Monolith** | The current system is too small for microservices. Stay with the modular monolith to keep developer overhead low and deployment simple. |
| **CI/CD Pipelines** | **Later** | Manual deployment via Git is acceptable for the current scale. Focus engineering time on core forensic features first. |

---

## 3. RISK-BASED PRIORITY PLAN

### Phase 1: Stability & Hardening (Immediate)
*Goal: Prevent runtime failures and secure the foundation.*
1.  **Production WSGI**: Transition from `app.run()` to **Gunicorn** or **Waitress** to handle concurrent requests safely.
2.  **Stateless Storage Prep**: Move file path references in the DB to use relative paths, making future S3 migration easier.
3.  **Security Audit**: Enforce strict CORS and rotate the `JWT_SECRET_KEY` to a 256-bit entropy string.

### Phase 2: Scalability & Performance (Short-term)
*Goal: Remove bottlenecks.*
1.  **Background Workers**: Integrate **Celery + Redis** to handle `/api/analyze` and `/api/batch`. This allows the server to return "Status: Processing" immediately.
2.  **API Rate Limiting**: Implement basic rate limiting per JWT to protect the AI engine from abuse.

### Phase 3: Production Grade (Advanced)
*Goal: High availability.*
1.  **Reverse Proxy**: Deploy **NGINX** as a frontend for the Flask app to handle SSL/TLS termination and static asset caching.
2.  **Containerization**: Move to **Docker-Compose** for localized environment isolation (App, DB, Redis).

---

## 4. TRADE-OFF EXPLANATION
*   **What are we NOT doing?**: We are avoiding Microservices. Splitting the auth, credits, and AI into different services would triple infrastructure costs and significantly slow down development with no current performance gain.
*   **Acceptable Risks**: Local file storage is a temporary risk. If the server goes down, files are currently on-disk. This is acceptable for a single-server pilot but must be addressed before multi-region deployment.
